# 完整验收样例

## 初始状态与入口

按 RUNBOOK 启动，访问 `http://127.0.0.1:18080`。使用从未出现的旅人编号（例如 `judge-20261116-a`）。无需预置记忆或知识库，第一次读取返回余额 0、未典当任何记忆、无线索。UI 自动生成每一步 request_id；每次点击「再次来访」生成新 session_id。实际运行记录与截图在 `evidence/`，均来自真实本地 Dify 和 PowerContext。

## 主样例：记住交易、找回妹妹

| 顺序 | 输入/操作 | 预期账本/反馈 |
|---|---|---|
| 1 | 点击推门进店，可输入“我想找妹妹。她说过：\"别忘了带伞。\"”及换行 | 第 1 次来访，0 币，无线索；能接受引号/换行 |
| 2 | 选红伞，典当 | 3 币，柜中有红伞 |
| 3 | 再次典当红伞 | 不得重复出售；仍为 3 币 |
| 4 | 点击合伞离店，再次来访 | 新 session，第 2 次来访；店主翻旧账，仍记得红伞和 3 币 |
| 5 | 问线索 | 消耗 2 币，剩 1 币；发现妹妹只认红伞，提醒需要赎回 |
| 6 | 选红伞，赎回 | 余额不足；交易不发生，仍为 1 币 |
| 7 | 选摇篮曲，典当 | 3 币；柜中红伞、摇篮曲 |
| 8 | 选红伞，赎回 | 0 币；柜中仅摇篮曲，记忆找回 |
| 9 | 走向终局 | 【带伞的人】：与妹妹相认，一起走出雨巷 |

这组样例的趣味在于：先卖掉看似普通的红伞，得到线索后才发现它正是相认的关键；需要牺牲另一段记忆才能弥补选择。金额、典当集合、线索和结局按表断言；模型对白可变化，无唯一标准文案。

## 对照样例：相同线索，不同后果

换一个全新旅人编号，按「进店 → 典当红伞 → 问线索 → 终局」顺序操作。应得到【擦肩】，不能把同一选择写成重逢。另有【迷途】（未买线索直接终局）、【无名归客】（买线索后保留红伞，但典当名字）两条规则分支。

## 自动验证

```bash
.venv/bin/python scripts/verify.py --output evidence/recheck.json
```

实际 17 项验证还包括：同一请求重试返回完全相同回执；一个请求只追加一次 Source；新玩家读不到旧玩家状态；复用请求编号却更换行动返回失败；非法玩家编号返回 422。实际 Dify workflow_run_id 随每步保存，可以对应 Dify 数据库中的工作流节点执行记录。PowerContext 证据含 scope_id、source_id、position、状态、玩家和会话；模型输出另有 `model.output` 事件。

实测记录：[acceptance.json](evidence/acceptance.json)；[对应实际事件](evidence/acceptance-events.jsonl)；[DSL 导入结果](evidence/import.json)。如果提供了 `workflow-nodes.json`，它是从真实 Dify PostgreSQL 读取并仅保留节点名、状态、耗时和错误的导出，不包含请求头或票据。

## 重置与跨进程恢复

每次复验换一个全新旅人编号即可恢复初始状态，无需清空任何数据库。自动脚本每次使用随机玩家前缀；历史故事保留以供核查。不要复用已终局的编号来测试初始状态。

跨进程恢复：先用新编号进店、典当红伞，Ctrl+C 停止 `native.py up`；重新执行 `up`，输入同一个编号并点击「再次来访」。应仍有 3 币和柜中红伞。这个过程读取 PowerContext 持久化 Source，不依赖浏览器内存或 Dify 会话变量。

实测已停止再启动全部服务，并通过同一个历史玩家的新会话恢复第 2 次来访，见 [restart.json](evidence/restart.json)。该记录证明来访次数跨进程保留；红伞跨会话的对照记录见主样例及 [再次来访截图](evidence/03-memory-return.png)。
